# Languages and countries (i18n): design, contracts and status

Goal (owner, 2026-10-27): a visitor in Spain sees the whole site in Spanish, a visitor in Germany in German, and so on; search
engines list each country's pages in that language; ads keep working everywhere. Written before the code so that the parts can
be built and translated in parallel against fixed contracts.

## 1. Which languages (measured, 2026-10-27)

Demand = Google Trends interest by country (12 months) for "audio to text / video to text / transcribe / subtitle generator" in
20 languages, times internet users (World Bank), cross-checked with the public traffic mix of seven competing tools (TurboScribe:
BR, US, ES, PE, IT; VEED: BD, IN, US, BR, ID; Notta: JP 69 %; Kapwing; HappyScribe: US, IN, PH, CO, PE; Vizard; Otter: US 67 %).
Top 20 markets: IN, US, ID, BR, PK, JP, MX, BD, EG, NG, TR, PH, FR, DE, TH, VN, ES, IT, GB, KR. English search terms are 60-95 % of
demand in every country; a native-language share of 10-30 % exists in every big market and is where competition is thinnest.
China (Google is not used), Iran (no Google ads) and Russia (Google ads paused for Russian users since 2022) are left out.
The raw data and scripts are not kept in the repository; the table is reproducible with Google Trends + World Bank.

## 2. URLs

* English: unchanged (`/`, `/video-to-text`, `/guides/srt-vs-vtt`).
* Every other language: a prefix, then a **localised slug** for tool pages and guides: `/es`, `/es/video-a-texto`,
  `/es/guides/<localised slug>`. Information pages and the two index pages keep their English slugs (`/es/faq`, `/es/how-it-works`,
  `/es/about`, `/es/contact`, `/es/privacy`, `/es/terms`, `/es/tools`, `/es/guides`). Transcript pages: `/es/jobs/<id>` (client
  only, noindex).
* A page exists in a language only when real translated content exists for it (`i18n/generated.ts`). English text is never
  published under a translated address.
* Pages of the language-specific English tool pages (`/hindi-audio-to-text`, `/spanish-audio-to-text`, ... and
  `/hinglish-transcription`) have no translated twin (a Spanish page about "Spanish audio to text" would just repeat the
  generic page). `/translate-audio-to-english` does.

## 3. How a string is translated

* **English text is the key.** Templates use `{{ 'Add another file' | t }}`, code uses `i18n.t('Add another file')`. English
  needs no dictionary and every existing test keeps passing. A missing translation falls back to the English text.
* Placeholders: `{name}` in the key, values passed as an object: `t('"{name}" is ready.', { name })`.
* Rich text (bold, links) in a sentence: `<app-rich [text]="'See {link}.' | t" />` with markup `**bold**` and `[label](/path)`;
  links render as real `<a href>` (localised through `i18n.path`) so crawlers and keyboards work.
* Dictionaries: `i18n/dict/<code>.ts`, `export default { 'English key': 'translation', ... }`, loaded lazily when a page of that
  language is opened (route resolver). Page titles, descriptions and labels are in the same dictionary under
  `title:<en path>`, `description:<en path>`, `label:<en path>` keys (title <= 60 characters with the brand).
* Long-form pages are content modules, not dictionary entries: tool pages (`features/tool-pages/content/i18n/<code>/<slug>.ts`,
  the same `ToolPageContent` shape) and guides (`features/guides/content/i18n/<code>/<slug>.ts`, `GuideContent`). The file name
  is the English slug; the localised URL slug lives in `i18n/slugs/<code>.ts`.
* A translator adapts, not transliterates: use the words people actually search (the native search terms per language are in
  section 6), keep every fact, never add a claim the English page does not make, keep the structure and the number of items.

### 3b. Wrapping a string (developers)

* Template text: `{{ 'Add another file' | t }}`. Attributes: `[attr.aria-label]="'Close' | t"`, `[title]`, `[placeholder]`.
  Placeholders: `{{ 'File {n} of {total}' | t: { n: i + 1, total: files().length } }}`.
* A sentence with bold or a link: `<app-rich [text]="'Read **How it works** or [ask us](/contact).' | t" />`.
* A link inside a translated page: `[routerLink]="'/faq' | lp"`; in code `this.router.navigateByUrl(this.i18n.path('/'))`.
* Code: `private i18n = inject(I18nService)` then `this.i18n.t('English', { n })`, inside a method called from the template
  or inside `computed()`, never in a constant or a field initialiser that outlives a language switch.
* A constant list shown later (`presets`, status labels): mark with `_t('Fastest')` (`i18n/mark.ts`) and show `{{ p.title | t }}`.
* One sentence = one key; never glue translated pieces into a sentence; no plural logic in a key (two keys instead).
* The key must be a literal string (the extractor reads source text). English output stays byte-identical, so every
  English test stays valid.
* Not translated on purpose: the operator Logs page, console and debug messages, file names, product names.
* After a change: `node scripts/extract-i18n.mjs` and commit `docs/in-browser/i18n-source.json` (translators read it);
  `node scripts/extract-i18n.mjs --check` fails when it is stale.

## 4. Pieces (contracts)

| Piece | File | What it does |
|---|---|---|
| Language list | `i18n/locales.ts` | codes, names, direction, Open Graph locale, hint text for the "also available in" bar |
| Service | `i18n/i18n.service.ts` | `locale()`, `dir()`, `t()`, `path(enPath)`, `alternates(enPath)`, `setLocale()` |
| Pipe, rich text | `i18n/t.pipe.ts`, `i18n/rich-text.ts` | `\| t`, `<app-rich>` |
| Slugs | `i18n/slugs/<code>.ts`, `i18n/slugs.ts` | English path -> localised slug |
| Availability | `i18n/generated.ts` | which English paths exist in each language (GENERATED by `scripts/gen-i18n.mjs` from the translation files) |
| Routes | `i18n/routes.ts` | clones the English route table under `/<code>` with localised slugs, a locale resolver and resolved titles |
| Switcher and hint | `i18n/language-switcher.ts`, `i18n/locale-hint.service.ts` | footer links + header menu; a dismissible bar offers the page in the browser's language, and only a language the visitor chose with the menu redirects (the English home only) |
| SEO | `core/title.service.ts`, `core/structured-data.service.ts`, `scripts/gen-sitemap.mjs` | `<html lang dir>`, `og:locale`, canonical, `hreflang` + `x-default`, `inLanguage`, sitemap alternates |

Auto-language rules (no forced redirects for crawlers): the visitor's browser languages (`navigator.languages`, never the IP
address) are read only in the browser. A guess is never acted on (Google advises against redirecting by a guessed language, changed
2026-10-27): on any page, the English home included, a different browser language only gets a small bar in the browser's
language that offers the same page there. A choice made with the switcher is saved (`localStorage vt-lang`) and respected: with a
saved choice of another language, landing on the English home `/` is replaced by `/<code>`. Googlebot (English, no preference,
no storage) never sees a redirect.

Self-hosted edition: `environment.languages` is `false`, no localised route exists, the backend and its tests are untouched.

## 4b. Countries, ads and search engines

* A country is not a language and not a URL: Spain, Mexico and Argentina share `/es`, Brazil and Portugal share `/pt`, Germany,
  Austria and Switzerland share `/de`. `hreflang` is the bare language code (Google's guidance for one page per language); no
  `es-MX` / `es-ES` split until there is real regional content to justify one.
* Ads: the same manual ad units on every language page (`data.ads` is copied from the English route, a spec checks it), none
  on the information, legal and transcript pages. Consent: Google's certified message for the EEA, UK and Switzerland is the
  owner's AdSense setting (*Privacy & messaging*, see `deploy/SEO.md` step 9); it speaks the visitor's language by itself. Not
  served: Iran, Cuba, North Korea, Crimea (sanctions) and Russia (paused by Google since 2022).
* Search engines: `<html lang dir>`, canonical (self), hreflang + `x-default` (English) both in the page and in the sitemap,
  `og:locale`, `inLanguage` in the structured data, a `Content-Language` header, translated titles and
  descriptions using the native search terms of section 6.

## 5. RTL (Arabic, Urdu)

`<html dir="rtl">` is set per page and the layout follows it (flex and grid flip by themselves). Every physical `left` / `right`
in the component styles is now a logical property (`margin-inline-start`, `inset-inline-end`, `text-align: start`, `border-inline-start`,
13 files). Done by hand because a property cannot flip them: the progress-bar origin (`job.scss`, `upload.scss`), the toggle knob,
the "list" icon, the indeterminate progress animation (`slide-rtl`). Always left to right inside an RTL page: code and subtitle
samples (`pre`, `code`, `.mono`), timecodes, the media player controls. The end of `src/styles.scss` also carries the typography per
script: font stacks that are already on the device (nothing to download), a taller line height for ar, ur, hi, bn, th, ja, ko, no
letter spacing (it breaks Arabic joins and Indic conjuncts), strict line breaking for Japanese, `keep-all` for Korean, hyphenation for
German, and `overflow-wrap: break-word` on headings only (an e-mail address in running text must stay whole). Urdu uses a Naskh stack,
not Nastaliq (Nastaliq needs a bundled font).

**Rule for `styles.scss`: never write a language rule on `html:lang(x)` alone.** The production build inlines each page's critical
CSS and defers the rest, and it drops a rule whose selector is only the root element. A font stack or line height in the deferred
file arrives about 250 ms after the first paint and reflows the page: cold-browser layout shift 0.544 on `/th/tools`, 0.286 on
`/ja/tools`. The rules are written as `html:lang(x) body { ... }` (`--font` is read by `body` only) and now measure 0.000 on every
translated page, desktop and phone, in a fresh browser. Check with a cold Chrome per measurement (a warm one hides it).

## 7. Translation rules (quality bar)

1. Translate meaning, not words; natural, current, neutral register (no slang, no machine-flavoured literalism).
2. Product names stay: TranscribeVid, Whisper, SRT, VTT, TXT, PDF, JSON, Markdown, WebGPU, WebAssembly. UI labels that appear in
   the interface (Quality, Language, Transcript style, ...) must be translated the same way everywhere (one glossary per
   language, kept in the dictionary).
3. Never invent a fact, number, feature, price, review or award. Keep every hedge ("often", "can", "may").
4. Titles <= 60 characters including " - TranscribeVid" (CJK and Thai: count characters, the limit is the same); descriptions
   50-160 characters; both contain a native search term when natural.
5. Keep placeholders (`{name}`), markup (`**bold**`, `[label](/path)`) and code samples (SRT / VTT / ffmpeg) exactly; translate
   only the visible words around them. Paths in links stay English paths (the app localises them).
6. Legal pages (privacy, terms) carry the note "This is a translation for convenience. If it differs from the English version,
   the English version applies."
7. British English is the source spelling; the target is the standard written form of that language (Brazilian Portuguese,
   Latin-American-neutral Spanish with Spain-neutral vocabulary, Modern Standard Arabic).
